# 招聘系统适配与动态表单设计

## 目标

在保持本地运行、用户主动触发、只写字段值且不扩大网页权限的前提下，提升不同招聘/投稿系统的兼容性。第一阶段覆盖两类问题：表单在首次扫描后异步出现，以及不同组件库需要结构化的控件识别和读写。北森先以可插拔适配器和脱敏夹具接入；拿到真实页面 DOM 后，再补充特征而不改动通用匹配流程。

## 设计

### 1. 适配器边界

`content.js` 保留现有的语义字段匹配、敏感字段过滤和填充安全检查。新增轻量适配器注册接口，每个适配器只声明：

- `name`：适配器名称；
- `matches(root)`：根据 DOM 结构或组件特征判断是否适用，不读取域名；
- `augmentControls(root, controls)`：补充通用选择器漏掉的控件；
- `read(control)` / `fill(control, field)`：只有组件需要特殊读写时才覆盖。

通用适配器始终作为兜底。站点名称只用于现有的本地草稿和映射，不成为权限或行为分支。北森适配器初始只覆盖常见的动态组件特征，未被真实 DOM 证实的规则必须由夹具和测试锁定后再加入。

### 2. 动态重扫

内容脚本在收到首次 `scan` 后，为当前页面文档和已发现的同源 frame 安装一个有上限的 `MutationObserver`。观察到新增控件或容器变化时只设置一次防抖标记，不在页面后台填充；弹窗再次发出 `scan` 时得到最新候选。新增 `refresh` 消息用于让弹窗在打开期间请求一次轻量重扫，并返回扫描代号与根节点统计。

观察器必须可拆卸，页面销毁、重新注入或调用 `clearScanObserver` 时断开；不得和网站记忆的控件观察器共用状态。防抖周期和最大触发次数固定，避免招聘页面的动画或无限滚动造成扫描风暴。

### 3. 诊断信息

扫描上下文返回适配器名称、扫描根数量、发现的控件数和跨域/closed root 的不可访问计数。这些信息只显示在弹窗状态或测试输出中，不包含字段值。未命中的候选仍由现有的“资料里没有/请确认”流程处理。

## 数据流

1. 用户点击扫描，弹窗注入最新版内容脚本并发送 `scan`。
2. 内容脚本发现适配器、收集通用与适配器补充的控件，按现有标签和资料匹配规则生成候选。
3. 内容脚本安装动态观察器并返回候选和诊断元数据。
4. 用户确认后，弹窗发送 `fill`；适配器只负责组件写入，提交/保存/上传控件仍被过滤。
5. 页面异步变化时，观察器只记录“需要重扫”；弹窗主动发送 `refresh` 获取新候选，不自动改变用户已确认的选择。

## 错误处理与边界

- 跨域 iframe、closed shadow root 和浏览器禁止注入的页面继续报告不可访问，不申请 `host_permissions`。
- 适配器抛错时降级到通用路径，并在诊断中记录适配器失败，不阻断其他字段。
- 动态重扫超过上限后停止观察，用户仍可手动再次扫描。
- 所有填充操作继续回读验证；失败项返回明确状态，不伪报成功。

## 测试

- 保留现有 Node 单测和各类 smoke 测试作为回归基线。
- 增加适配器单测：匹配、补充控件、适配器失败降级。
- 增加动态夹具：首次扫描为空，异步插入字段后 refresh 能发现，连续 mutations 只触发一次防抖扫描，submitAttempts 始终为 0。
- 增加北森风格脱敏夹具：表单容器、动态下拉、单选组和 portal 浮层；不把未经真实页面验证的域名或选择器写入逻辑。
- `sites-smoke.ps1` 增加北森及其他投稿系统的字段措辞分组，继续要求关键字段精确命中和至少 80% 可用。
